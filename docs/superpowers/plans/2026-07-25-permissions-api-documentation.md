# Permissions API Publication and Documentation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish the complete permissions OpenAPI contract to the central Scalar reference and document the REST-only plugin integration, runtime behavior, authentication, manifest model, and troubleshooting flow in `docs.grounds.gg`.

**Architecture:** `service-permissions` owns the deterministic OpenAPI source of truth and publishes it through the shared workflow. `api-reference` validates and serves that immutable snapshot in Scalar. The `docs` repository explains product concepts and operational usage while linking to Scalar for field-level API schemas.

**Tech Stack:** OpenAPI 3.1, SmallRye OpenAPI, GitHub Actions, Scalar, TypeScript/Next.js, Mintlify MDX

## Global Constraints

- Publish the complete REST API, including administration, runtime, and environment sync endpoints.
- Never hand-edit generated endpoint schemas in `api-reference`; the released service snapshot is authoritative.
- OpenAPI security schemes are `portalBearer` and `workloadBearer` and must be applied per operation.
- Error responses use RFC 9457 `application/problem+json`.
- Scalar is the field-level reference. Mintlify docs explain workflows, security boundaries, failure semantics, and examples without duplicating the full schema.
- Do not document gRPC or `PERMISSIONS_GRPC_TARGET` as a supported path.
- Explicitly state that runtime HTTP is cluster-internal for this release and link transport encryption follow-up `groundsgg/grounds-pulumi#298`.
- Never include live tokens, kubeconfigs, internal host credentials, or personal player data in examples.

- [ ] **Step 1: Write the section landing page**

- [ ] **Step 2: Document plugin integration**

- [ ] **Step 3: Document runtime behavior**

Describe the two-second request timeout, no immediate snapshot retry, valid-cache fallback, fail-closed login, local evaluation, `refreshAfter`/`expiresAt`, asynchronous manifest registration, retryable statuses, terminal statuses, and removal of `RefreshOnlinePlayers`.

- [ ] **Step 4: Document runtime authentication**

Explain projected ServiceAccount tokens, audience `service-permissions`, per-request token rereads, TokenReview, path-based SubjectAccessReview, capability-to-path mapping, `401` vs `403` vs `503`, `automountServiceAccountToken: false`, and why Portal and workload bearer tokens are not interchangeable. State that transport is internal HTTP for this release and link issue `grounds-pulumi#298`.

- [ ] **Step 5: Write troubleshooting guidance**

Create symptom-led sections for:

- login denied when the service is unavailable;
- token file missing/unreadable;
- `401` invalid token or audience;
- `403` missing capability/source;
- `409` catalog source collision;
- `503` Kubernetes review dependency unavailable;
- manifest retries without registration;
- stale snapshot/cache expiration;
- runtime Service DNS/port mismatch.

For each, provide safe checks and log fields to correlate (`requestId`, workload namespace/ServiceAccount, source, status) without printing a token.
